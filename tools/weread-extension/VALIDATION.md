# 0.1.0.17 内存修复验证

2026-09-11。用户反馈 Edge 在自动翻章一段时间后出现 `Out of Memory`。
代码中发现书页启动会加载整本旧缓存、导出会创建整本对象及 JSON 字符串，且连续 SPA
翻章没有定期重载。这些是内存风险；未取得崩溃时的堆快照，不能认定其中某项是唯一原因。

## 自动回归

`pnpm --filter @jojo/weread-extension test`：14 项通过。
覆盖分片落盘、旧缓存合并、导出完整性、翻章停止/续传、每页 8 章限制、恢复章节计数、
高内存提前重载、Worker 不可用时保留缓存并报错，以及安装备份和重复应用。

## 独立浏览器验证

使用本机 HTTP 测试页和单独浏览器配置，不操作用户的微信读书标签页。

- 完整原始 WRX JSON：133,468,379 字节，1,077 条目录（包含封面），1,076 条正文记录。
- 在 Worker 中将前 128 章放入旧整本记录，其余放入 v2 逐章记录，模拟混合缓存升级。
- v3 恢复结果：1,076 / 1,076，目录完整；再次恢复不启动迁移 Worker。
- 再次恢复耗时约 37 ms，逐章 Blob 导出约 1.5 秒（本机单次测量，不含网络）。
- 输出 133,468,380 字节。逐章检查全部 5,380 个字段无差异，目录与元数据一致；
  输出时间和测试页来源变化不计入正文比较。
- 缓存恢复及导出期间，每 25 ms 采样的测试页主线程 JS 堆峰值约 6.2 MB。
  这是 `performance.memory` 的采样值，不是总进程内存，不含 Worker 和微信读书页面。
- 用单独的 MV3 扩展配置加载相同 store/Worker 代码，隔离环境中的缓存和导出成功。
- 用相同 auto/store/Worker 代码在模拟阅读页连续保存 25 章，实际跨文档重载 3 次，
  最终 25 / 25，每章仅采集一次，无页面脚本异常。

实际已登录 Edge 的自动操作被 Windows 控制工具停止，原因是无法可靠识别当前浏览器地址。
因此以上测试不代替真实微信读书长时间翻章；用户需重新加载扩展并刷新阅读页使更新生效。
