## 26 家 24 小时批次

并发修复后的 GitHub 全量 HTTP 验证发现 856 篇文章，25/26 家 feed 可用，795 篇原页成功、61 篇失败，
生成 66.5 MiB WACZ；采集、归档、解析、构建分别耗时 12.8、36.9、98.8、16.6 秒，总耗时
165.1 秒。第一财经 RSSHub 三次均返回 503；证券时报 feed 成功但窗口内为 0 条。61 个原页失败来自
Bloomberg 19 篇、NYT 20 篇、FT 9 篇、Axios 8 篇的 403，以及 NPR 5 篇未得到最终响应。规范化交付
为全文 336、部分正文 1、摘要 519；parser 报告无运行错误。“摘要”不影响原始 HTTP 响应已进入
WACZ，后续可以离线新增 parser 后重放。本地对照为 858 篇、总耗时 259.3 秒，结果一致。

在全量测试前，GitHub Chromium 抽样发现 853 篇文章，从其中选择 26 篇、覆盖全部 24 家有候选文章的来源：
21 篇成功、5 篇失败，生成 51.4 MiB WACZ。采集、浏览器归档、解析、构建分别耗时 59.4、77.5、
4.6、7.9 秒，流水线总耗时 149.4 秒；包含安装 Chromium 和上传 artifact 的完整 Action 为 182 秒。
失败样本为 NYT 403、Reuters 401、FT 403、Axios 403 和 Indian Express 403；Bloomberg 浏览器样本
从普通 HTTP 的 403 提升为 200。第一财经 feed 仍为 503，证券时报窗口内没有候选文章。

首次覆盖 25 家的抽检曾在 8 分钟上限被终止。定位发现部分页面产生上千个资源响应，旧实现虽限制
WACZ 字节数，仍会读取全部响应并串行读取 header。修复后每次页面尝试保留主文档和最早 127 个子资源，
并在统一 5 秒预算内并行读取正文和 header；同一批次浏览器归档降到 77.5 秒。

随后对滚动 24 小时窗口执行了 8 个 Chromium 分片，并对并行发现阶段超时的 SCMP、联合早报做串行
恢复。合并后 25/26 家 feed 可用，共发现并尝试 800 篇文章；532 篇返回 2xx/3xx 页面，268 篇返回
限制页：Reuters 96 篇为 401，Indian Express 127 篇、NYT 16 篇、Axios 3 篇为 403，Bloomberg
19/20 篇和 FT 7/9 篇为 403。第一财经仍为 503，证券时报窗口内 0 条。归档共保存 60,632 个网络
响应，响应正文 2.23 GiB，生成 8 个主 WACZ 加 1 个恢复 WACZ，合计 1.134 GiB；只有 5 个响应因
单响应上限被截断。主 8 分片 wall time 为 10 分 59 秒，最慢分片流水线 411.5 秒；恢复分片另耗时
428.2 秒。这个结果纠正了此前把 66.5 MiB HTTP 主文档包称为“一天全量”的错误。

生产流程据此改为每十分钟最多 50 篇 Chromium 增量捕获。冷启动 24 小时积压需要多轮消化，稳定态
每十分钟新增量远低于 50；正文发布与原页归档仍使用同一提交顺序，失败页保留状态并按两小时重试。

## 已排除来源

The Wall Street Journal 已从生产来源目录移除。补充的 GitHub Actions 审计在同一份订阅快照内，
对 307 个 Mihomo 配置有效节点逐一启动独立 Chromium：269 个返回 401、9 个返回 403、27 个网络
失败，只有 2 个返回 200。这 2 个节点随后在原 job 内连续测试 3 篇当前文章；每篇两次 baseline
均稳定返回 200，但只有约 148–184 个可见词，而且都含明确的继续阅读/订阅提示，因此是预览而非
全文。

同一节点、同一快照的 Browsertrix 对照分别生成 baseline 和已启用 BPC 的 WACZ。两种归档的最大
HTML 正文区同为 1,683 字符、最大页面文本同为 5,456 字符，BPC 没有增加正文。此前另一份 305
节点快照也没有全文候选。节点序号会随订阅更新漂移，所以候选复测必须在同一 job 内完成，不能在
后续运行中按序号重新选择。基于这些结果，不再让 WSJ 占用十分钟生产任务的抓取预算。

“技术可得”与“可由 JOJO 存储并经公共 CDN 再分发”是两个问题。项目已声明取得所需授权；实现仍把
存档和 Delivery 内容策略分开，以便按来源记录允许的字段、地域、时效和访问控制，并独立启用全文策略。
